\section{Implementation Architecture of the Prototype}
\label{sec:implementation-architecture}

Where the design chapter described the experiment from the participant's point of view, the present section describes how the prototype was implemented as a coherent software pipeline. The main goal of the implementation was not merely to make each task work in isolation, but to ensure that input handling, effect application, task execution, logging, and analysis were structured consistently enough that the resulting data could later be compared and interpreted within one shared workflow. In practice, this required the Unity side and the RShiny side to be designed together: the Unity runtime needed to expose stable event and sample data, and the Shiny application needed to reconstruct these data into interpretable summaries, quality measures, spatial plots, and trajectory plots.

The implemented system can therefore be understood as four connected layers. First, the Unity runtime receives embodied or controller-based input and normalizes it through a central controller script. Second, the task scripts use this normalized input to run the individual baseline, exposure, and post-exposure procedures under the active perturbation. Third, two custom logging scripts translate the runtime state into a session structure composed of metadata, discrete events, continuous samples, and summary rows. Finally, the RShiny dashboard reads these files back in and visualizes the completed sessions through a unified analysis interface. Figure~\ref{fig:implementation-pipeline} summarizes this red thread from participant action to post-hoc analysis.

\subsection{Central Runtime Orchestration}
\label{subsec:implementation-runtime}

The central implementation decision was to organise the Unity prototype around \texttt{SandboxRunner.cs}. Rather than allowing each task to query controllers, hand rays, calibration anchors, and perturbation logic independently, the runner acts as the single orchestration layer. It is responsible for initializing references, handling calibration, selecting the active task and effect mode, progressing from baseline to exposure to post-exposure, and providing a unified input representation to the task scripts. This is important because the project does not only compare different visual perturbations; it also compares controller-based interaction with embodied hand-based interaction. By resolving these two modalities into the same \emph{transformed input} interface, the rest of the runtime can treat them as different implementations of the same experimental pipeline instead of as separate applications.

The second central file in the runtime is \texttt{PrismCore.cs}. This script collects the effect abstractions used by the prototype, including the neutral \emph{no effect} condition together with \emph{translation}, \emph{rotation}, and \emph{skew}. The important implementation point is that the effect layer is kept separate from the task layer. In other words, Open-Loop Pointing, Line Bisection, Landmark, and Exposure do not each implement their own perturbation logic. Instead, the runner requests the current effect transform from \texttt{PrismCore.cs}, applies it to the active input representation, and only then passes the transformed result to the task scripts. This separation makes it possible to keep the task logic comparatively clean while still switching effects at runtime.

Although the runtime is centered on the runner and the effect layer, three smaller support scripts help present the interaction clearly enough for the participant to perform the tasks. \texttt{HandDwellProgressBar.cs} drives the dwell-confirmation and transition progress visualization, making the embodied confirmation state and the between-trial timing readable without exposing unnecessary implementation details. \texttt{RoundedRectGraphic.cs} generates the rounded UI geometry used by that progress indicator so the interface can be constructed directly in Unity rather than through external textures. \texttt{DepthQueGradient.cs} serves a different purpose: it colors the scene's depth-cue stripes to strengthen the participant's sense of forward distance toward the target wall. These scripts are not analytically central in the same way as the runner or the effect layer, but they close the loop between the formal task structure and the participant's actual perceptual experience of the prototype.

\subsection{Task-Specific Execution}
\label{subsec:implementation-tasks}

On top of the shared runtime sit the four task scripts: \texttt{OpenLoopPointingTask.cs}, \texttt{LineBisectionTask.cs}, \texttt{LandmarkTask.cs}, and \texttt{ExposureTask.cs}. All four consume the unified input supplied by \texttt{SandboxRunner.cs}, but each script defines its own stimulus construction, acceptance rule, and task-specific measurement logic.

\texttt{OpenLoopPointingTask.cs} implements the simplest measurement task. The script creates one visible target, waits for the participant to adopt the required posture, accepts a single response, and records the signed endpoint error relative to the intended target center. Its main function is therefore to translate one accepted pointing response into a stable per-trial measurement that can later be compared between baseline and post-exposure blocks. \texttt{LineBisectionTask.cs} reuses much of the same structural logic, but replaces the point target with a displayed line. The implementation difference is that the accepted response must be interpreted relative to the line's true midpoint, making the main output a signed midpoint error rather than a signed endpoint deviation. \texttt{LandmarkTask.cs} differs more strongly from the other two: instead of pointing toward one location, the participant chooses which of two line segments appears longer. The script therefore constructs a split stimulus, randomizes which side is objectively longer, and reduces the participant's response to a categorical left/right decision and a correctness measure.

\texttt{ExposureTask.cs} is implemented separately because it serves a different experimental purpose. Rather than isolating one accepted response, it drives repeated acquisition of one of three horizontally arranged targets under the currently active perturbation. The task script cycles among left, center, and right targets, judges each confirmed attempt as hit or miss, tracks the count of successful hits, and signals back to the runner when exposure is complete. This is also the file in which the participant-facing feedback is most explicit: target highlighting, hit markers, and the center-target visual cue all belong to the exposure implementation because they are part of what makes the adaptation phase legible as a repeated target-to-target task.

What ties these four scripts together is that they all adopt the same experimental grammar even though the stimuli differ. Each task defines how a trial or attempt is started, how the participant's input is interpreted, when a response is accepted, and which values must be written to the logger. The implementation is therefore modular, but not fragmented: different task scripts solve different local problems while remaining aligned to one shared runtime and one shared logging format.

\subsection{Logging as the Bridge Between Unity and Analysis}
\label{subsec:implementation-logging}

The most important implementation bridge between Unity and the later analysis is the custom Prism logging layer. Two project-specific scripts were created for this purpose: \texttt{PrismExperimentLogger.cs} and \texttt{PrismSampleLogger.cs}. Although both write CSV rows through the inherited \texttt{LoggingManager}, they serve different roles and should be understood as complementary rather than redundant.

\texttt{PrismExperimentLogger.cs} writes the discrete structure of the run. It stores session metadata, block transitions, accepted measurement trials, exposure attempts, target spawns, exposure completion, and block- or task-level summaries. It also decides whether a session should count as \emph{Finished} or \emph{Aborted}, based on whether the participant actually passed through baseline, exposure, and post-exposure. This file is therefore the implementation counterpart to the experimental logic described in the design chapter: it records not only what the participant did, but in which phase, under which effect mode, with which input mode, and under which confirmation condition the action occurred.

\texttt{PrismSampleLogger.cs}, by contrast, writes the continuous time series. At a fixed sampling rate it stores the currently transformed pointer ray, head pose, controller poses, movement-anchor poses, dwell state, confirmation state, and the current task context such as block, trial, attempt, and target index. This is the file that later enables the RShiny dashboard to reconstruct approach trajectories and compute the acceleration, deceleration, and hover phases that were added during the project. The distinction between the two loggers is therefore analytically important: the experiment logger captures \emph{discrete structure}, whereas the sample logger captures \emph{continuous movement}.

This logging architecture is also where the project's concern for consistency becomes most concrete. The same run is represented in four collections --- \texttt{Meta}, \texttt{Event}, \texttt{Sample}, and \texttt{Summary} --- and each collection contributes a different perspective on the same session. By keeping the field names and block/task labels stable across these collections, the implementation makes it possible to reconstruct the same experimental run in different ways without needing a different loader for every task and every effect.

\subsection{RShiny Analysis Layer}
\label{subsec:implementation-rshiny}

The final script in the PEGFG implementation is \texttt{app.R}, which serves as the entry point to the local RShiny analysis dashboard. In implementation terms, this file is not merely a plotting script; it is the analysis-side counterpart to the Unity logging layer. The app first discovers completed sessions by grouping together the separate \texttt{Meta}, \texttt{Event}, \texttt{Sample}, and \texttt{Summary} CSV files belonging to the same session. It then loads the selected session into memory and derives a series of task-specific data structures that can be reused across tabs. In practice, this means that the same raw logs can be viewed as single-session summaries, cross-session comparisons, quality checks, spatial hit distributions, or projected approach trajectories.

Within \texttt{app.R}, the logic is organized around a set of helper functions that each transform one part of the logging schema into a more interpretable view. Summary helpers reconstruct aftereffect interpretations from \texttt{Summary.csv}. Quality helpers turn accepted trials or exposure attempts into outlier counts, trend lines, and hit-rate summaries. Spatial helpers interpret event rows differently depending on whether the selected task is Open-Loop, Line Bisection, or Exposure. Trajectory helpers combine \texttt{Event.csv} and \texttt{Sample.csv} so that one accepted exposure attempt can be reconstructed as a projected aim path on the target plane. Finally, the Shiny server logic binds these helpers together through reactive expressions, so that changing the selected session or task automatically updates the visible cards, tables, and plots.

This part of the implementation is essential for the project's overall red thread. Without the Shiny layer, the Unity prototype would produce data, but the data would remain opaque. Without the structured Unity logging layer, the Shiny app could not reconstruct the run in a reliable way. The implementation chapter should therefore present Unity and R as two parts of the same system rather than as separate deliverables: the prototype produces structured sessions, and the analysis interface turns those sessions into digestible evidence.

\subsection{Implementation Red Thread}
\label{subsec:implementation-red-thread}

Taken together, the implementation follows a consistent red thread from interaction to interpretation. \texttt{SandboxRunner.cs} ensures that different input modalities and perturbation modes can be treated within one runtime grammar. The task scripts then operationalize the individual measurement and exposure procedures while reusing that shared grammar. The Prism logging layer converts these runtime events and trajectories into a stable session structure, and \texttt{app.R} reconstructs the same structure into analysis views that can be read session by session or compared across runs. For the report, this means the implementation chapter does not need to describe the prototype as a set of unrelated scripts. Instead, it can present the prototype as one layered system whose parts were designed to support one another: runtime control, task execution, logging, and analysis.
